# SimpleX outbound alert transport and opt-in runtime

This standalone Java 25 module is a single-shot outbound alert transport for an already running SimpleX Chat v7.0.0 service and one explicitly configured, already established numeric contact. The repository's parent POM remains unchanged and does not build this module. The [opt-in runtime runbook](../docs/simplex-alert-runtime.md) contains the separate contained deployment; the [Java monitor](../docs/java-monitor.md) produces scheduled alerts. It contains no incoming-message handler, command dispatch, group, AI, admin, provisioning, retry, or service-management workflow.

Build from this directory with `mvn package`. The executable shaded JAR is `target/simplex-alert-0.1.0-SNAPSHOT.jar`. Set `SIMPLEX_ALERT_ENDPOINT` to `ws://127.0.0.1:<port>/` or `ws://[::1]:<port>/`, set `SIMPLEX_ALERT_CONTACT_ID` to a positive signed 64-bit contact ID, and supply one UTF-8 alert on standard input. The independent transport accepts either literal loopback address, but the bundled pinned v7 runtime binds only IPv4 and fixes its endpoint to `ws://127.0.0.1:17619/`; `[::1]` will not reach that bundled server. Input is read to EOF and must be 1–4000 bytes; newline bytes are part of the alert. The program writes only a result name to stdout. There is no automatic retry. Do not put alert text in command-line arguments or logs.

- `ACCEPTED` (exit 0): the correlated local SimpleX response identified one sent chat item for the configured contact. Recipient delivery remains unknown.
- `REJECTED` (exit 2): the correlated command returned a recognized error. This alone does not prove the absence of side effects; do not treat it as a safe automatic retry instruction.
- `NOT_SUBMITTED` (exit 3): a send was never attempted.
- `UNKNOWN` (exit 4): an attempt may have reached SimpleX, but acceptance is unconfirmed. Retrying may duplicate an alert.
- `INVALID_INPUT` (exit 64): input or configuration was invalid before submission.

The stdin reader waits for EOF and has no input deadline; a producer that leaves the pipe open can stall the program. After input, the CLI applies the configured 10-second timeout separately to connection, transmission, and acknowledgment, so these phases can take roughly 30 seconds in total, plus scheduling overhead; there is no overall deadline. Library calls are synchronized per transport instance and may wait for another call to finish. An external deadline or process termination after submission can leave the outcome unknown, so a caller must not assume a retry is safe.

Neither the transport nor the entry point logs the endpoint, destination, alert, or error details. **The upstream v7.0.0 SimpleX WebSocket server itself prints the entire command to stdout**, including destination and content ([Server.hs](https://github.com/simplex-chat/simplex-chat/blob/v7.0.0/apps/simplex-chat/Server.hs#L118-L126)). Before use, the operator must address this separately. Directing both process stdout and stderr to nonpersistent discard sinks from startup avoids persistence through those streams, but does not prove other files, crash dumps, supervisors, or subprocess paths are free of sensitive output; it also removes diagnostics. The transport cannot enforce this. SimpleX maintains its own message storage.

Loopback restricts routing but does **not** isolate or authenticate the service: other local processes or processes sharing its network namespace may reach it, and a malicious local service can impersonate it. Service lifecycle, isolation, contact identity, and access controls are operator responsibilities. The v7 server consumes a shared event queue for each WebSocket client, so a dedicated SimpleX process is required to avoid disturbing another client. No service is started, provisioned, or contacted by the tests.
